# LifeTrail Phase 2 — Processed Timeline, OSRM and Published Daily Snapshots

Status: ready-for-agent
Labels: ready-for-agent
Type: spec
Date: 2026-10-06

## Problem Statement

The Owner can currently inspect a Device's Raw GPS Route and replay it, but must infer journeys, stops and missing data from individual observations. GPS jitter, impossible jumps, long stationary periods and missing observations can produce misleading geometry and playback. A raw daily LineString can connect places where no movement was observed.

The Owner needs a truthful daily account of Trips, Stops and GPS Gaps, including transport modes and road-matched Routes where evidence supports them. The account must remain useful when OSRM is unavailable, when late Batches arrive or when the Owner changes timezone. Cross-midnight activity must retain its meaning, and refresh must not replace a useful published view with partially rebuilt data.

## Solution

Extend the existing Daily Map, Timeline, selection and playback experience with server-derived continuous activity. Preserve Raw GPS unchanged, derive Trips containing ordered Movement Segments, detect Stops and GPS Gaps, and explicitly disclose Evidence Holes. Match sufficiently confident walking, cycling and driving segments through internal self-hosted OSRM services; publish safe raw-derived fallback where matching is unavailable or unreliable.

Store immutable range-based Activity Revisions, compose them through versioned Activity Manifests, and project that history into immutable Published Daily Snapshots using the Owner's current IANA timezone. Keep the last successful publication readable while refresh runs or fails. Activate affected snapshots atomically after verifying input generation, processing target and worker authority.

The Web reads persisted snapshots and lightweight publication status. Route Parts with historical progress anchors and server-owned cumulative vertex distances drive playback and daily clipping. The application explains missing observations separately from observations that do not provide enough evidence, without animating invented travel through either interval.

## Implementation Decisions

1. **Baseline and boundaries.** Extend the current Vue Option 2 application shell, Daily Map, Timeline, Pinia selection/playback state and MapLibre camera behavior. Keep firmware collection, durable recording and synchronization unchanged. Rust/Axum owns processing and persisted read models; PostgreSQL/PostGIS owns storage. Modules remain separated by quality, segmentation, classification, matching, activity composition, projection, job orchestration and publication responsibilities.
2. **Raw source of truth.** Raw GPS is immutable. Processing neither updates nor deletes accepted GPS Records. Firmware using the existing gps/1 Batch protocol continues to upload unchanged. Derived rebuilding creates new versions rather than replacing Raw GPS.
3. **Activity ownership.** Trip, Stop, GPS Gap and Movement Segment belong to a Device's continuous UTC history, not exclusively to a processed calendar day. Daily View is a projection/publication boundary.
4. **Trip semantics.** A Trip is a maximal continuous chain of supported movement ending at a confirmed Stop or GPS Gap. It contains one or more ordered Movement Segments. Mode changes and pauses below qualifying Stop criteria do not themselves end the Trip. Evidence uncertainty may leave its boundaries open rather than assert continuity or confirmed termination.
5. **Stop semantics.** Detect Stops before matching using spatial dwell, duration and quality/context, not speed equal to zero alone. Server derives center and radius. Repeated visits separated by movement remain distinct. Suggested initial radius and minimum dwell are 30 meters and 180 seconds, configurable and subject to fixture tuning.
6. **GPS Gap semantics.** Detect actual temporal absence between known Raw observations using a configurable threshold, before quality filtering. No GPS Gap precedes the first or follows the last Raw observation. Do not infer movement/Stop, call OSRM to fill it, add connector distance or animate across it.
7. **Evidence Holes.** Existing observations that cannot support reliable activity/geometry create unresolved evidence coverage rather than an artificial GPS Gap. Activities adjacent to a hole may have open boundaries inside history. Do not claim both sides form one Trip or infer a Stop. Expose projected evidence_holes separately from Timeline events with interval, reason and Raw point count. Reasons include insufficient quality, ambiguous activity, insufficient geometry and unsupported classification; matcher failure alone is not a hole when valid fallback is available.
8. **Actual and observed boundaries.** Activity has actual started_at/ended_at, observed_from_at/observed_until_at, and confirmed/open start/end boundary states. Actual boundaries are null when open. Observed duration is the observed interval length; full duration is known only when both actual boundaries are confirmed. Never extrapolate an open interval to the current time or calendar-day end.
9. **Range expansion.** Start from dirty input and expand in both directions until segmentation outside the effective range is unchanged and boundaries are semantically safe. A fixed context-hour window does not define correctness. Observation edges and verified Evidence Hole edges preserve their appropriate open semantics.
10. **Technical versus semantic boundaries.** Replacement endpoints require independently semantic-safe Trip/Stop boundaries, verified Evidence Hole boundaries or verified observation edges. A processing-window edge qualifies only if semantic-safe. Validated chunk seams authorize Route Part assembly only, never Activity Revision splitting by themselves. A requested replacement inside a continuous activity expands to semantic-safe activity boundaries.
11. **Classification.** Deterministic time-window evidence feeds a persistence/hysteresis state machine. Require an enter-confidence threshold and sustained duration for transitions, with a lower exit threshold. Short compatible unknown intervals may collapse under an unknown-grace policy; sustained unknown intervals remain separate. Confidence, mode windows, persistence and grace are centrally configurable.
12. **Profile selection.** Sufficiently confident walk/bike/car select OSRM foot/bike/car respectively. Unknown or below-threshold candidate modes use raw fallback. Do not try all profiles to infer mode from a plausible match. Matching success is not proof of travel mode.
13. **OSRM deployment.** Add three internally reachable Docker Compose services for car, bike and foot; do not publish their ports to the LAN by default. Each uses a separately prepared profile dataset from a bounded OSM extract covering acceptance journeys, using extract, partition, customize and MLD serving. Image/tag and profile/dataset preparation details remain implementation choices; pin and record the actual engine/dataset identities used.
14. **OSRM responsibilities.** Match is the historical processing service; Route supports road-network simulator generation; Nearest is an internal diagnostic utility. Browser access is through LifeTrail's read API, not direct OSRM calls. MapTiler remains basemap/style provider and MapLibre remains renderer.
15. **Matching inputs.** Preserve usable source mapping, temporal order, segment boundaries and meaningful turns while reducing redundant points. Convert original millisecond timestamps to seconds without generating adjusted timestamps. Same-second selection uses usable status/explicit quality rank, lower known HDOP, more known satellites, earlier original timestamp and GPS Record ID as deterministic tie-breaks. Missing metadata ranks after known values. Retain matcher index, source ID/time, converted time and selection reason; disclose detail lost to second resolution.
16. **Chunking and seams.** Bound Match requests with configurable overlapping chunks; initial suggestions are 80 points and five-point overlap. Seam evidence uses shared source observations, time, progress and tracepoint locations. Require compatible temporal/progress direction and geometric separation within configured tolerance. Deterministically rank valid seams by quality, geometry separation, bearing discontinuity when available, overlap midpoint proximity and source ID. Never merge by dropping a fixed number of output vertices or inventing a connector.
17. **Radii and confidence.** GPS metadata supplies no exact horizontal accuracy. Estimate radius from HDOP and a configurable error factor, or use a configurable fallback radius. Confidence thresholds and partial-match policies are processing configuration, not protocol invariants. Preserve input/matched/outlier counts and selection/fallback reasons.
18. **Route Parts.** A Movement Segment may have zero or several contiguous drawable Route Parts. A published matched part requires valid geometry, known observed temporal coverage and valid historical anchors. Safe temporally mapped hybrid matched/raw parts are allowed. If safe mapping or seam boundaries cannot be established, use fallback for the whole affected Movement Segment. Never fabricate a second coordinate to force a LineString or turn matcher failure into a GPS Gap.
19. **Canonical playback geometry.** Ordered route_parts are canonical; a derived daily MultiLineString is optional overview convenience. Each part identifies its Movement Segment, source, observed coverage, LineString, distance and progress anchors. Anchor timestamps increase strictly, distances are non-decreasing within part length, and start/end anchors are provided. No timestamp-per-OSRM-vertex contract applies.
20. **Server-owned distance.** Each part publishes vertex_distance_m aligned one-to-one with geometry coordinates, starting at zero and non-decreasing, with the final value matching part distance within numerical tolerance. Web uses this metric and the temporal anchors rather than independently recomputing Route length. Playback interpolates progress between anchors, then locates the coordinate along the supplied vertex progress.
21. **Daily clipping.** Use the Owner's current IANA timezone and the interval from local midnight to next local midnight, with UTC storage. Clip activity on observed bounds only. Distinguish actual/observed/visible intervals and expose open states; continuation flags mean observed coverage extends outside the selected day, not inferred unobserved continuation. Clip Route Parts using anchored progress and synthetic calendar-boundary anchors, rebasing visible vertex/anchor progress to zero. Daily distance is the difference in original progress at clipping endpoints; adjacent day totals conserve part distance within tolerance.
22. **Summary.** point_count includes every Raw GPS Record in the local day, independently of usable quality. Expose usable count and optionally excluded count, whose sum cannot exceed total count. First/last observation timestamps follow the Raw set or are null when empty. Sum trip_duration_s, stop_duration_s and gap_duration_s only over observed daily intersections. Short pauses belonging to Trips count as Trip duration, not asserted physical motion. Event counts count strictly positive observed overlap in that day, including crossing events in each relevant day. Distance sums published clipped parts only, with no rejected geometry or implicit connectors.
23. **Evidence state.** Separate sufficient, partial and insufficient activity evidence from processing/freshness/matcher quality. Sufficient covers considered observed activity apart from explicit GPS Gaps; partial has reliable activity plus unresolved coverage; insufficient supports no reliable activity. One point or entirely unusable records can publish a successful empty processed view. Safe raw fallback alone does not imply partial evidence.
24. **Immutable Activity Revisions.** A revision owns one continuous processing range, its processing target/input generation, explicit superseded range, events, ordered segments, parts and matcher evidence. It is immutable after successful creation. Reuse unchanged versions outside safe replacement cuts instead of copying full Device history. Activity revision identity is distinct from daily publication identity.
25. **Canonical Activity Manifests.** Immutable manifest versions explicitly compose ordered, non-overlapping half-open UTC slices referencing precise safe revision coverage. A slice may reuse a safe subset of an older revision. Overlapping replacements splice the current manifest to create a canonical new one; readers never infer precedence from newest revision IDs. Manifest coverage does not invent history outside known observations.
26. **Immutable Daily Snapshots.** Each published snapshot pins its source manifest and immutable activity versions with local date, timezone identity/generation, source Raw and processed-through generation, reducer/projection schema versions, creation time and freshness provenance. Reads use pinned sources rather than whatever manifest becomes active later. Only activation pointers are mutable.
27. **Processing and freshness axes.** Background work uses idle, queued, running and failed states; publication availability/freshness uses current, stale and unavailable. Retain the last good processed snapshot through queued/running/failed refresh. Empty-but-valid insufficient evidence is processing success. Separate activity freshness from projection freshness so a new-timezone projection can disclose stale source without claiming it covers current input.
28. **Input generation.** Advance monotonic per-Device input_generation exactly once in the transaction committing a new valid Batch, including late, overlapping or poor-quality data. Replay, conflict, authentication/validation failure and rollback never advance it. Configuration, dataset, processing-version, timezone and reprocessing requests use separate target identities and do not alter Raw generation.
29. **Durable work and capture.** PostgreSQL stores coalesced per-Device dirty work. One in-process server worker satisfies acceptance without imposing a one-Device schema constraint. A durable control row serializes ingestion, target changes and publication. Merge dirty ranges and persist scheduling with ingestion; work arriving during a running job must not be lost. Capture input/targets consistently and finish input-read transactions before OSRM processing.
30. **Claims and crash recovery.** Claim jobs in short transactions using row locking with skip-locked behavior, reclaimable leases and monotonically renewed fencing authority. Persist attempts/requested ranges. A reclaimed worker with an older token cannot publish even if its input/target still match. Processing may create duplicate temporary candidates, but publication is idempotent and cannot activate a candidate twice.
31. **Activity activation.** Build candidates outside the publication transaction. A short control-row-serialized transaction verifies current input generation, processing/projection target identities and fencing authority, then activates activity/manifest and all affected daily snapshot pointers together. Any mismatch rejects activation, retains prior publication and requeues current work. Cross-midnight changes cannot publish half old and half new projections.
32. **Timezone-only reprojection.** Timezone changes rebuild projections, summaries, clipping and visible parts only, never quality/segmentation/classification/OSRM. Never relabel an old-timezone snapshot. Reproject the latest published manifest even if its activity source is stale relative to pending Raw input; retain truthful source-generation/freshness metadata. Activation checks expected active manifest, current Owner timezone generation and valid projection-job fencing. Reject and requeue when either source changes. Projection-only jobs never modify activity publication state. Until an appropriate projection exists, Raw Daily View with status is valid fallback.
33. **API ownership.** Evolve the canonical Device/day Daily View and add a lightweight Device/day status endpoint through the canonical OpenAPI contract, generating Web types. Full responses carry one complete published snapshot, processing/freshness/provenance, evidence state, summary, projected Timeline events, evidence_holes and Route Parts. Status carries state/freshness/publication/input generation and projection identity without geometry. Preserve nonexistent-Device versus existing-empty-day behavior and gps/1 ingestion compatibility.
34. **Web refresh.** Poll status every five seconds only while queued/running and visible. Stop on idle/failed/hidden; immediately refetch status when focus or visibility returns. Fetch the complete Daily View once when publication changes, replace displayed data atomically and clear selection/pause/reset playback. Query identity includes Device, date and timezone/projection identity; stale responses cannot relabel or overwrite the current context.
35. **Map and playback behavior.** Extend existing selection to Trip/Stop/Gap event IDs; Trip selection highlights/fits visible geometry, Stop selection focuses center/radius, and map selection updates Timeline. Stop UI distinguishes unknown actual endpoints from observed times/duration. Preserve play/pause/restart/seek, speed controls, Course-Up/Heading-Up and look-ahead camera with final overview. Gap playback holds the last observation, discloses the interval and jumps at the next observed timestamp; do not interpolate disconnected parts or Evidence Holes.
36. **Identity.** Event IDs are stable across projections within their creating activity revision only. Reprocessing may merge/split activities and change IDs without reconciliation. Snapshots may reuse unchanged source-revision event IDs; publication change still resets UI selection/playback.
37. **Matcher evidence and determinism.** Retain actual input, request parameters/hash, source selection mapping, engine/profile/dataset versions, normalized results or failures, confidence/status, attempts/timing, and seam decisions/fallback reasons. A hash alone is insufficient for audit/replay. Fixed Raw input, processing version/config and matcher input/evidence produce deterministic normalized derived results; online matching and outage evidence need not produce identical geometry.
38. **Finite retry and reprocessing.** Retry transient connection/timeouts/network/selected server failures within configurable attempt, delay and total-time budgets. NoMatch, valid low confidence and invalid matcher input go directly to processing policy. Exhaustion prefers safe fallback over dependency-induced failure. Published fallback never upgrades automatically on OSRM recovery; explicit reprocessing creates a new revision/publication.
39. **Retention.** Phase 2 does not automatically delete Activity Revisions, manifest versions, Daily Snapshots, matcher candidates/evidence or rejected/superseded candidates. Not active does not imply safe to delete. Preserve historical referenced readability and measure storage; future GC must be reference-aware reachability.
40. **Simulator.** Generate routes from OSRM Route between scenario waypoints, sample in logical historical time and emit valid gps/1 Batches. Seed deterministic speed variation, acceleration, jitter, low quality, jumps, missing GNSS, revisits, returns, U-turns, repeated roads, Stops, short pauses and mixed modes. Retain protocol validity despite intentionally degraded processing evidence.
41. **Acceptance scale and measurements.** Baseline is one Owner, one Device, up to 30,000 GPS Records per Owner-local day, a bounded extract covering acceptance and one processing job at a time. Measure Raw/usable counts, OSRM requests, processing wall time, peak/representative memory, Daily View payload size and DB read latency. Also measure revision bytes, manifest count, snapshot bytes, candidate bytes and matcher-evidence bytes. Agree time/resource budgets after benchmarking on the target machine, rather than inventing an SLA.
42. **Delivery boundaries.** Separate domain/persistence/publication foundation, quality/gap processing, segmentation, classification, OSRM infrastructure/client, matching, activity/daily composition, API/Web integration, playback and simulator acceptance. Infrastructure can proceed alongside segmentation; matching depends on segmentation semantics and the OSRM client. API/UI integration consumes the generated contract; playback consumes the Route Part contract. No monolithic Phase 2 processor module.

## Testing Decisions

1. **Primary seam already agreed.** Use the accepted feature-level flow: valid Batch upload through the public HTTP ingestion contract, real worker processing and PostgreSQL/PostGIS persistence, then Daily View/status reads and Web behavior. This carries forward the confirmed end-to-end acceptance and race cases; no new interview or seam approval is required for synthesis.
2. **Existing prior art.** Existing server integration tests drive the Axum Router with real PostgreSQL/PostGIS for provisioning, atomic Batch commit/replay/conflict, Raw daily projection, DST, deterministic point ordering, empty/single-point days and missing Devices. Existing Vitest coverage exercises the generated API client/query boundary, Timeline models, Pinia state, playback math/controller/camera and map lifecycle. Existing Python tools test exact Batch bytes/manifests and HTTP replay. Extend these seams rather than building a parallel harness around each internal processing helper.
3. **Matcher dependency seam.** Introduce a fake OSRM-compatible HTTP boundary for deterministic success, partial output, outages and invalid results while exercising the real processing/publication flow. Separately run bounded live-OSRM Docker acceptance for car/bike/foot preparation, Match/Route reachability and simulator integration. Assert normalized behavior for frozen evidence; do not require evolving OSM data to reproduce old routes.
4. **Test behavior.** Assert public response semantics, observable state transitions, retained Raw/history, published geometry/time/coverage and atomic visibility. Use persisted inspection where essential to prove Raw immutability, generation/fencing effects and historical reference retention. Avoid tests coupled to private helper call order, table naming or incidental implementation structure.
5. **Raw invariants.** Compare accepted GPS Records before and after processing/reprocessing. Verify an impossible jump leaves Raw GPS intact but contributes no derived geometry/distance. Verify quality filtering creates no artificial GPS Gap and processing never changes protocol timestamps.
6. **Evidence and sparse days.** Exercise zero data, one observation, all unusable observations, stationary-only data and mixed reliable/poor-quality coverage. Check valid success/empty results, truthful counts, sufficient/partial/insufficient independent of raw fallback, and distinct GPS Gap/Evidence Hole messages. Do not infer activities outside observed bounds.
7. **Trip/Stop semantics.** Assert WALK then CAR without Stop/Gap is one Trip with two ordered segments. Assert short pauses stay in Trip time, qualifying dwell becomes a Stop and repeated visits remain separate. Exercise mode oscillation, persistence, brief unknown grace and sustained unknown segments.
8. **Open activity.** Assert nullable actual boundaries, known observed bounds, nullable full duration and daily clipping without now/end-of-day extrapolation. Exercise open boundaries both at dataset edges and beside interior Evidence Holes, including late observations that extend or close them.
9. **GPS Gaps.** Inject an actual Raw timestamp absence between observations. Assert an explicit Gap, no Stop/movement inference, no distance connector, no matcher filling and no animated interpolation. Low-quality records at the same timestamps must produce different evidence behavior.
10. **Cross-midnight projection.** Assert a 23:50–00:20 Stop remains one source event, contributes 10/20 minutes to neighboring days and counts once in each view. Exercise crossing Trips and Route Parts with synthetic midnight anchors, observed continuation flags and source IDs shared across projections of the same revision. Include DST/local-day cases using the existing timezone-aware integration seam.
11. **Geometry/progress properties.** Check coordinate/vertex-distance length agreement, zero origin, non-decreasing bounded distances, matching final part length, strictly increasing anchor times and valid part coverage. Check exact stable seek results, loops/U-turns and no interpolation between disconnected parts. Use explicit numerical tolerances, not visual plausibility alone.
12. **Distance conservation.** Assert daily clipped distance equals progress differences, adjacent day distances sum to original part distance within tolerance, and boundaries/connectors/rejected geometry add no extra distance. Verify hybrid matched/raw parts contribute only their published lengths and Web consumes supplied metric.
13. **Reduction/chunking.** Exercise same-second ties, nullable metadata, turn preservation, long traces and overlapping chunks. Check deterministic source selection without fabricated timestamps. Require seam evidence based on shared observations/time/progress and test safe seams, divergent roads, deterministic ties and fallback on unsafe seams; do not accept duplicated output geometry.
14. **Safe matched publication.** Provide attractive matched geometry with invalid anchors or unknown temporal mapping and assert rejection. Test safe hybrid parts within one segment and whole-segment fallback when partial boundaries cannot be trusted. Matcher failures never create a GPS Gap.
15. **Dependency failure.** Exercise successful matching, NoMatch, low confidence, transient timeout/server failure and retry exhaustion. Assert finite attempts/time budget and usable fallback publication. After OSRM recovers, historical publication remains unchanged until explicit reprocessing.
16. **Determinism and provenance.** Replay fixed matcher evidence with pinned Raw/config/version and compare normalized derived outputs. Confirm source mappings, attempts, seam decisions, normalized failures and actual matcher inputs remain available; do not equate online and outage runs.
17. **Generation and replay races.** Assert one generation increment per new valid committed Batch, including late/overlap/poor-quality input. Sequential and concurrent identical replays, conflicts, failed authentication/validation and rollbacks never advance it. Race a new Batch against activation and assert no outdated candidate becomes current.
18. **Target races.** Change processing config/version/dataset or projection timezone while a candidate runs without changing Raw generation. Assert stale-target activation fails and current work remains queued; unchanged Raw generation is not sufficient authority.
19. **Crash/fencing/idempotency.** Claim with token 41, expire/reclaim with token 42, then allow the old worker to finish: token 41 cannot publish. Restart after staged candidate creation and after activation; verify recovery, no duplicate activation and retained prior snapshots. Coalescing during a running job must not lose new dirty input.
20. **Atomic multi-day publication.** Read while replacing a crossing activity and assert every snapshot is internally complete and activation changes affected daily pointers together. Failed/refused refresh leaves the last successful publication readable and stale, rather than switching it to Raw or exposing candidate rows.
21. **Manifest splice authority.** Exercise a replacement inside an existing revision, followed by overlapping replacement across several slices. Check ordered non-overlapping half-open manifest entries, exact safe slice coverage, old references outside replacement, and snapshot-pinned interpretation independent of revision recency.
22. **Semantic boundary safety.** For a continuous Trip on [A,D) and validated seam C with A < B < C < D, a requested [B,C) replacement must expand beyond technical seams to semantic-safe boundaries. A seam coinciding with an independently established Trip boundary may authorize replacement because of the Trip boundary, not the seam.
23. **Timezone/source races.** Start a projection on manifest M17/timezone T6, publish M18, then attempt activation: reject the M17 candidate. Repeat with T6 changing to T7. Verify projection-only work never alters activity publication. Permit new-timezone projection of G142 while G143 is pending with STALE_SOURCE and correct processed-through metadata.
24. **Historical retention.** Keep snapshot S5 referencing M10/R10 while M11 supersedes R10 with R11. Normal processing, refresh and publication must leave S5/M10/R10 readable, along with rejected candidates and matcher evidence. Observe storage growth without automatic deletion.
25. **Web status and snapshot replacement.** Use fake timers/status responses to check five-second lightweight polling only while visible queued/running, stopping on idle/failed/hidden and immediate focus/visibility refresh. Unchanged revision does not redownload geometry; changed revision fetches once and replaces a complete response while clearing selection/resetting playback. Prevent old timezone/revision responses from replacing the current context.
26. **Map/Timeline/playback acceptance.** Verify Trip focus/highlight, Stop focus/radius, reverse map selection, open Stop labels, debug Raw/processed display, historical-time seeking, Gap/Evidence Hole explanations and preserved camera/end overview. Use component/controller seams for logic and a browser acceptance run for actual rendered interactions.
27. **Realistic full system acceptance.** Generate and ingest a seeded road-network day with Home/Coffee/Office/Restaurant/Supermarket/return visits, mixed modes, long and short Stops, jitter, one impossible jump, poor HDOP and a GNSS Gap. Add focused variants for multimode Trips without Stops, cross-midnight events, late Batch refresh/failure and fallback reprocessing. The flow completes through processing, API, Web and playback without manual DB editing.
28. **Operational acceptance.** Verify OSRM services are internally reachable without LAN port exposure, historical reads succeed while they are offline, geometry is persisted and the page does not create a DOM marker per GPS Record. Record the agreed 30k-day processing/payload/latency/memory/storage measurements; pin scenario, versions, config and machine details for comparison.
29. **Implementation checks.** Run relevant server formatting, unit/integration tests and strict linting; generated OpenAPI/Web type checks, Web tests/build; simulator/protocol tests and Compose acceptance appropriate to the delivered changes. Tests requiring PostGIS/live OSRM must explicitly run in their supporting environment rather than be mistaken for passed checks when skipped.

## Out of Scope

- Web login, multi-user authorization, public Internet deployment and TLS/ACME.
- Changes requiring a firmware upgrade or changing existing gps/1 ingestion semantics.
- Moving Trip/Stop/classification/map-matching logic into firmware.
- Live tracking, photos, audio, media timelines, video export, AI place recognition, semantic search, automatic POI naming and geofence automation.
- BLE/captive-portal provisioning and rebuilding the existing Option 2 application shell or camera experience.
- OSRM as basemap/renderer, browser-facing OSRM ports, or planned navigation features.
- Guessing transport mode by trying every matching profile, filling unobserved routes or treating technical seams as activity boundaries.
- Stable event identity reconciliation across reprocessing merges/splits.
- Automatic fallback upgrades, scheduled matcher-upgrade policies and automatic processing-data garbage collection.
- Redis/Kafka queues, distributed processing requirements or a concurrency/scale target beyond the agreed acceptance baseline.
- Vietnam-wide OSRM deployment as a condition of Phase 2 completion.
- A processing-time SLA before target-machine benchmarks.
- Required SSE/WebSocket invalidation, separate geometry download APIs, optional Smart playback/stop compression and optional automatic target-duration playback presets. These can follow later; historical-time playback is required now.
